## DBを表で考える

**データベース（DB）**は、情報を整理して保存し、必要なものを取り出す仕組みです。**テーブル**は表、**行**は1件の情報、**列**は情報の項目です。SupabaseはDBやログイン機能を提供するクラウドサービスです。クラウドは、ネット経由で使う外部のコンピューターのサービスを指します。

| 列 | 意味 | 例 |
| --- | --- | --- |
| id | タスクを区別するID | 自動生成されるUUID |
| user_id | 持ち主のID | ログインした利用者のID |
| title | タスク名 | 教材を開く |
| done | 完了したか | false |
| created_at | 作成日時 | 自動記録される日時 |

UUIDは重複しにくい長い識別子です。`true`／`false` のように2つの状態を表す値を真偽値と呼びます。

## SQLで表とルールを作る

**SQL**はDBへ構造や操作を伝えるための言語です。今回は `supabase/schema.sql` を読み、学習用DBで一度実行します。`create table` は表の作成、`not null` は値が必須、`check` は入力の制限です。SQL全体を暗記する必要はありません。

## 認証と認可を分ける

- **認証**：「あなたは誰か」を確認。今回はメールアドレスとパスワードでログイン。
- **認可**：「あなたは何をしてよいか」を確認。今回は自分のタスクだけを読んで変更。
- **RLS（Row Level Security）**：DBの行ごとに認可を行う仕組み。

RLSの条件 `auth.uid() = user_id` は「ログインした人のIDと、この行の持ち主が一致する」という意味です。利用者AがURLに利用者BのタスクIDを書いても、DBが許可しません。画面で非表示にするだけでは保護になりません。[Supabase公式のRLS解説](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 演習と判断

[演習3](../exercises/03-database.md)で同じコードの保存先をSupabaseへ切り替えます。ローカルのタスクは自動移行しないため、最初の一覧は空で正常です。

利用者Aで作り、Bでは見えず、Aに戻ると残っていることを確認します。「ログインできた」だけでは完了せず、「他人のデータを扱えない」ことまで確かめます。

振り返り：ログインとRLSの役割をそれぞれ1文で説明してください。接続できなかった場合は、何を確認できて何が未確認かを記録します。未確認の権限設定を「安全」と評価しないことが大切です。
