# 第1〜3回の解答・講師メモ

[カリキュラム](../curriculum.md)

## 第1回

1. 画面は入力を受けて依頼を送る。バックエンドは内容を確認し、保存を頼む。保存先は後で読むために残す。
2. 色と余白はCSS、文字や項目の構造はHTML、操作への反応はJavaScript。
3. demoモードのデータは `app/data/tasks.json`。ブラウザ内だけに保存しているわけではない。
4. 保存実験のメモはブラウザ内。通常の再読み込みでメモリは消え、sessionStorageとlocalStorageは残る。新しいタブへURLを手入力するとlocalStorageの値は共有され、sessionStorageは別になる。
5. ブラウザの保存値は利用者が変更できるため、権限はバックエンドとDBで確認する。別端末とデータを共有するには同期の仕組みが必要で、このアプリはSupabaseのDBを使う。

補足質問の答え：ReactのJSXは通常JavaScriptへ変換してから使い、ブラウザが直接JSXを実行するわけではありません。ログインのセッションは本人として扱う状態・期間、sessionStorageはタブ内の保存機能であり、別の意味です。

見出しの変更箇所は `<h1>` の中、色は `--accent` と `--accent-dark`。CSS変更でデータが変わらないことも確認します。

## 第2回

追加はPOST/201、編集と完了はPATCH/200、削除はDELETE/204、一覧はGET/200。204は本文なしの成功なので、表示欄が空でも異常ではありません。

空白だけ・81文字は400。80文字は201。画面を経由せずAPIを呼べるため、サーバー側の入力確認が必要です。Consoleで追加しても、画面を再描画する処理が動かないので「一覧を再読み込み」で反映します。

## 第3回

認証は利用者を確かめること、認可は操作を許す範囲を確かめること。RLSは、利用者のIDと行の持ち主IDが一致するかをDBで確認します。

期待する結果：AはAの行を、BはBの行を読める。A/B間の他人の行の更新・削除はできない。管理者のTable Editorで両方が見えるのは別権限のためです。

`POST /api/session` が成功しても、SQL未実行ならタスク操作は失敗します。「ログイン成功」と「DBの設定完了」を分けて確認してください。publishableキーはアプリの識別、トークンは利用者の識別であり、RLSを回避する管理者キーは使いません。
